## Purpose

Transform a structured feedback record — whether a customer churn signal, a feature request, or an automated improvement finding — into a formatted GitHub issue body. The output is a JSON object containing `title`, `labels`, and `body` that can be passed directly to `gh issue create` or the GitHub MCP without further processing.

This skill is **pure-transform**: it makes no API calls, writes nothing to the repo, and has no external side effects. It is the bridge between the loop's autonomous improvement signals and the engineering backlog.

## Inputs

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `title` | string | yes | — | Issue title (displayed as the GitHub issue headline) |
| `type` | `bug \| feature \| improvement \| churn-signal` | yes | — | Category of the issue; drives label assignment |
| `source` | string | no | `"loop"` | Origin attribution — customer name/ID, cron agent name, or mission ID (e.g. `"customer:acme-corp"`, `"improvement-hunter"`, `"M-20260522-1234-..."`) |
| `description` | string | yes | — | Raw feedback text or finding body; used to populate `## Details` and derive `## Proposed action` |
| `severity` | `critical \| high \| medium \| low` | no | `"medium"` | Urgency level; becomes a `severity:<level>` label |
| `labels` | string[] | no | `[]` | Additional GitHub labels to attach beyond those auto-derived from `type` and `severity` |

### Input validation

Before processing, validate that all required inputs are present and `type` is one of the four allowed values. On failure, return immediately with the error object described in the Failure modes section — do not attempt partial processing.

## Process

1. **Validate inputs.** Check `title`, `type`, `description` are non-empty strings. Check `type` ∈ `{bug, feature, improvement, churn-signal}`. If `severity` is supplied, check it ∈ `{critical, high, medium, low}`. On any failure, return the appropriate error object and stop.

2. **Map type to base labels.**

   | `type` | Base GitHub labels |
   |--------|--------------------|
   | `bug` | `["bug"]` |
   | `feature` | `["enhancement", "customer-feedback"]` |
   | `improvement` | `["enhancement"]` |
   | `churn-signal` | `["churn-signal", "customer-feedback"]` |

3. **Build full label list.** Start from the base labels, add `"severity:<severity>"` (e.g. `"severity:high"`), then append any caller-supplied `labels` (deduplicated, lowercase, hyphens only — strip spaces, convert to lowercase).

4. **Render issue body** using the following template (Markdown):

   ```
   ## Summary

   <one-sentence description derived from title and the first sentence of description>

   ## Source

   <source attribution>

   ## Details

   <description verbatim>

   ## Proposed action

   - <action bullet 1 derived from description>
   - <action bullet 2, if applicable>
   - <action bullet 3, if applicable>

   ## Acceptance criteria

   - <measurable done-definition bullet 1>
   - <measurable done-definition bullet 2, if applicable>

   ---
   *Generated by gh-issue-from-feedback skill — <ISO timestamp>*
   ```

   Guidance for derived sections:
   - **Summary**: one sentence, imperative mood, ≤120 chars. If the `description` already opens with a one-sentence summary, use it verbatim; otherwise synthesise from `title`.
   - **Proposed action**: 1–3 concrete action bullets inferred from `description`. For `bug` type: first bullet is "Reproduce and confirm"; for `churn-signal`: first bullet is "Schedule retention call with customer". Keep each bullet ≤80 chars.
   - **Acceptance criteria**: 1–3 measurable done-definitions. For `bug`: first AC is the bug no longer repros. For `feature`/`improvement`: first AC is the feature is live and tested. For `churn-signal`: first AC is customer acknowledgement received.

5. **Check body length.** If the rendered `body` exceeds 65 000 characters, truncate `description` so the total stays within limit and append `\n\n> *[description truncated — original exceeded 65 000 chars]*` immediately before the `---` footer. Emit a `warning` key in the output (see Output section).

6. **Return JSON output** (see Output section).

## Output

### Success

```json
{
  "title": "Fix webhook retry storm on payment failure",
  "labels": ["bug", "severity:high"],
  "body": "## Summary\n\nFix the webhook retry loop that saturates the queue on payment failures.\n\n## Source\n\ncustomer:acme-corp\n\n## Details\n\nWhen a Stripe webhook fails, BullMQ retries every 5 seconds...\n\n## Proposed action\n\n- Reproduce and confirm the retry loop in staging\n- Add exponential back-off with jitter to the webhook worker\n- Add a dead-letter queue alert\n\n## Acceptance criteria\n\n- Bug no longer reproduces in staging under simulated payment failure\n- Dead-letter queue alert fires within 60 s of exhausted retries\n\n---\n*Generated by gh-issue-from-feedback skill — 2026-05-22T24:10:00Z*",
  "shell_command": "gh issue create --title \"Fix webhook retry storm on payment failure\" --label \"bug\" --label \"severity:high\" --body \"<body above>\""
}
```

The optional `shell_command` key is a convenience hint — a ready-to-copy `gh issue create` invocation. It is not required for programmatic callers using the GitHub MCP.

### Success with truncation warning

```json
{
  "title": "...",
  "labels": [...],
  "body": "...",
  "warning": "description-truncated",
  "shell_command": "..."
}
```

## Failure modes

| Condition | Return value |
|-----------|-------------|
| `title` missing or empty | `{ "error": "missing-required-input", "field": "title" }` |
| `description` missing or empty | `{ "error": "missing-required-input", "field": "description" }` |
| `type` missing or empty | `{ "error": "missing-required-input", "field": "type" }` |
| `type` not in allowed enum | `{ "error": "invalid-input", "field": "type", "allowed": ["bug", "feature", "improvement", "churn-signal"] }` |
| `severity` not in allowed enum | `{ "error": "invalid-input", "field": "severity", "allowed": ["critical", "high", "medium", "low"] }` |
| Body exceeds 65 000 chars after truncation logic | Truncate and set `"warning": "description-truncated"` (not an error — still returns success shape) |

## Integration points

| Consumer | Invocation context | Notes |
|----------|--------------------|-------|
| Head of Customer Success agent | Churn signal detected in CS review | Passes `type: "churn-signal"`, `severity: "high"` or `"critical"` |
| Head of Product agent | Feature request from customer interview | Passes `type: "feature"`, `source: "customer:<id>"` |
| `improvement-hunter` cron | Tech debt / code-quality finding | Passes `type: "improvement"`, `source: "improvement-hunter"` |
| Operator (manual) | Ad-hoc feedback triage | Any valid input combination |

## Constraints

- Pure-transform: never calls Write, Edit, Bash, or any external API.
- `Read` tool is listed in the manifest for context lookup only (e.g. reading architecture files for context) — the core transform requires no file reads.
- Does not create GitHub issues itself — output is JSON for the operator or an MCP caller to submit.
- Scoped to inputs provided in the invocation; never reads the target repo's files as part of its core logic.
