# gh-issue-from-feedback skill

## What it does

The `gh-issue-from-feedback` skill converts a structured feedback record into a ready-to-submit GitHub issue. Given a title, type, description, and optional metadata, it returns a JSON object with a `title`, `labels`, `body`, and a convenience `shell_command` you can paste directly into a terminal.

The skill is **pure-transform** — it makes no API calls and writes nothing to the repo. It is the standard bridge between the Bevox autonomous loop's improvement signals and the GitHub engineering backlog.

## Why it exists

Bevox generates customer feedback signals through multiple channels: CS reviews that flag churn risk, product interviews that surface feature requests, and the `improvement-hunter` cron agent that identifies technical debt. Without a shared formatting contract, each agent would produce inconsistent issue bodies — different label schemes, missing acceptance criteria, no source attribution.

`gh-issue-from-feedback` provides that contract. Any agent that needs to open a GitHub issue calls this skill, gets back uniform JSON, and submits via `gh issue create` or the GitHub MCP. The result is a backlog where every issue has the same structure, the same label taxonomy, and a clear audit trail back to its origin.

## Inputs

| Parameter | Type | Required | Default | Description |
|-----------|------|----------|---------|-------------|
| `title` | string | yes | — | Issue headline |
| `type` | enum | yes | — | `bug`, `feature`, `improvement`, or `churn-signal` |
| `source` | string | no | `"loop"` | Origin: customer name/ID, agent name, or mission ID |
| `description` | string | yes | — | Raw feedback text or finding |
| `severity` | enum | no | `"medium"` | `critical`, `high`, `medium`, or `low` |
| `labels` | string[] | no | `[]` | Extra GitHub labels beyond auto-derived ones |

`type` drives the base label set:

| Type | Auto-applied labels |
|------|---------------------|
| `bug` | `bug` |
| `feature` | `enhancement`, `customer-feedback` |
| `improvement` | `enhancement` |
| `churn-signal` | `churn-signal`, `customer-feedback` |

A `severity:<level>` label is always added (e.g. `severity:medium`).

## Output

The skill returns JSON:

```json
{
  "title": "Add in-app onboarding checklist for new workspaces",
  "labels": ["enhancement", "customer-feedback", "severity:medium"],
  "body": "## Summary\n\nAdd an in-app checklist to guide new workspace admins through initial setup...\n\n## Source\n\ncustomer:bevox-staging\n\n## Details\n\nMultiple customers mentioned during onboarding calls that they were unsure what to do after signing up...\n\n## Proposed action\n\n- Define the 5–7 checklist steps with the CPO\n- Build the checklist component in the dashboard\n- Track checklist completion in the analytics pipeline\n\n## Acceptance criteria\n\n- Checklist is visible on first login for new workspace admins\n- Completion rate is tracked and accessible in the analytics dashboard\n\n---\n*Generated by gh-issue-from-feedback skill — 2026-05-22T10:30:00Z*",
  "shell_command": "gh issue create --title \"Add in-app onboarding checklist for new workspaces\" --label \"enhancement\" --label \"customer-feedback\" --label \"severity:medium\" --body \"...\""
}
```

The `shell_command` field is a ready-to-run terminal command. For programmatic submission via the GitHub MCP, use `title`, `labels`, and `body` directly.

## Usage examples

### Churn signal from Head of Customer Success

The Head of CS agent has identified that Acme Corp has not logged in for 14 days and mentioned pricing concerns in the last support ticket.

```
gh-issue-from-feedback:
  title: "Acme Corp churn risk — pricing objection + low engagement"
  type: churn-signal
  source: "customer:acme-corp"
  severity: high
  description: |
    Acme Corp (15-seat plan, $1,200/mo) has not logged in since 2026-05-08.
    Their last support ticket (2026-05-06) mentioned that they found the pricing
    "hard to justify" given current feature set. NPS score: 4/10.
    Recommend scheduling a retention call and offering a feature preview.
```

Result: issue labelled `churn-signal`, `customer-feedback`, `severity:high` — ready to assign to the CS lead.

### Feature request from Head of Product

```
gh-issue-from-feedback:
  title: "Export OKR progress as PDF for board meetings"
  type: feature
  source: "customer:board-request"
  severity: medium
  description: |
    Three enterprise prospects asked whether the OKR dashboard can produce
    a one-page PDF summary for board pack distribution. Current workaround
    is a screenshot, which does not scale. Should support per-Objective
    filtering and a Bevox-branded header.
  labels: ["enterprise", "reporting"]
```

Result: issue labelled `enhancement`, `customer-feedback`, `severity:medium`, `enterprise`, `reporting`.

### Tech debt finding from improvement-hunter cron

```
gh-issue-from-feedback:
  title: "Replace synchronous Stripe webhook handler with BullMQ worker"
  type: improvement
  source: "improvement-hunter"
  severity: medium
  description: |
    The /webhook/stripe endpoint processes events synchronously inside the
    request handler (routes/stripe.ts:42). Under load this risks timeouts
    and duplicate processing. Standard pattern is to enqueue immediately
    and process in a BullMQ worker with idempotency checks.
```

Result: issue labelled `enhancement`, `severity:medium` — queued in the engineering backlog.

## Failure handling

If a required input is missing or `type`/`severity` is not one of the allowed values, the skill returns an error object without creating any output:

```json
{ "error": "missing-required-input", "field": "description" }
```

```json
{ "error": "invalid-input", "field": "type", "allowed": ["bug", "feature", "improvement", "churn-signal"] }
```

Callers should check for an `error` key before attempting to use `title`, `labels`, or `body`.

If `description` is very long (> 65 000 characters after rendering), the skill truncates it and adds `"warning": "description-truncated"` to the output — the issue is still created, just with a shortened description.

## Which agents invoke this skill

| Agent | Trigger | Typical type |
|-------|---------|-------------|
| Head of Customer Success | Churn signal detected in weekly CS review | `churn-signal` |
| Head of Product | Feature request from customer interview or support ticket | `feature` |
| `improvement-hunter` cron | Code quality gap or tech debt finding | `improvement` |
| Operator (manual) | Ad-hoc triage of inbound feedback | Any |

## Submission methods

**Terminal (operator-driven):**
Copy the `shell_command` from the output and run it in the repo root. The `gh` CLI must be authenticated.

**GitHub MCP (agent-driven):**
Pass `title`, `labels`, and `body` to the `create_issue` MCP tool. No shell access required — the MCP handles authentication.
